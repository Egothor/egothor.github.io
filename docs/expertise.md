<section class="section section--tinted">
  <div class="shell section-heading section-heading--split">
    <div><p class="section-kicker">Engineering posture</p><h2>Research depth without research theatre.</h2></div>
    <p>Work is expected to make the underlying model visible: assumptions, state transitions, runtime constraints, tests and performance evidence should be concrete enough for another engineer to challenge.</p>
  </div>
  <div class="shell principle-grid">
    <article><span class="principle-index">01</span><h3>Explicit models</h3><p>Architecture should reveal the security, data and state model rather than leaving it implicit in incidental implementation behaviour.</p></article>
    <article><span class="principle-index">02</span><h3>Lean runtime paths</h3><p>Preparation and validation can be complex when they make the production path smaller, faster and easier to reason about.</p></article>
    <article><span class="principle-index">03</span><h3>Evidence over assertion</h3><p>Tests, benchmarks, deterministic artifacts and structured reports are part of the engineering model, not release decoration.</p></article>
  </div>
</section>
